# Database

Drizzle schema, client and migrations shared by the API (and later the web app). PostgreSQL only.

## Layout

- `src/schema/<domain>/<table>.ts`: one table per file, re-exported by the domain `index.ts` and by `src/schema/index.ts`. Import as `@nowly/database/schema/<domain>`.
- `src/client.ts`: `createDatabase(url)` returns `{ db, pool }`; `Database`, `Transaction` and `Executor` types.
- `src/migrate.ts`: `migrateDatabase(url)`, used by `pnpm --filter @nowly/database migrate` (Docker start) and the integration tests.
- `migrations/`: SQL generated by drizzle-kit. Never edit a migration that has shipped.

## Schema rules

- The tables were created by Prisma. Table, column, index, primary and foreign key names (`users_email_key`, `sessions_user_id_fkey`, `sync_documents_pkey`) must keep the Prisma names: a rename is a destructive migration in production.
- Timestamps are `timestamp(..., { withTimezone: true, precision: 6 })`. `Announcement` is the exception (camelCase columns, `timestamp(3)` without time zone, as Prisma created it): keep the server in UTC until a dedicated migration converts it.
- Foreign keys are named and declared with `foreignKey(...)`, `onUpdate("cascade")` and the explicit `onDelete`.
- New table or column: edit the schema, run `pnpm --filter @nowly/database generate`, review the SQL (no `DROP`, no type change that rewrites data without a plan), commit both.

## Migrating from Prisma without data loss

- Migration `0000` is the baseline: exactly the schema produced by the 21 Prisma migrations (checked by diffing `pg_dump --schema-only` of both).
- `migrateDatabase` detects a Prisma database (`public.users` exists, `drizzle.__drizzle_migrations` does not) and records `0000` as applied without running it, then applies the later migrations. A new database gets `0000` normally. It is idempotent.
- `_prisma_migrations` stays in production and is ignored. Do not drop it in the same release.
- Production rollout: back up first (`pg_dump`), deploy, let the container run `migrate`, then check that `drizzle.__drizzle_migrations` holds the `0000` row and that row counts are unchanged. Never run a migration against a live database without explicit authorization.
